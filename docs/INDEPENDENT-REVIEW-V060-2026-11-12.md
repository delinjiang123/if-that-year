**从 v0.20 到 v0.60，这个项目把上一轮审核里几乎所有“系统层”的扣分项都做掉了——影子成了真模拟、职业线整线闭环、判词与收费都动了真格。它现在的问题不再是“做得不够”，而是三件收尾期的事：文档口径与现网不一致、一份公开读数始终没有出现、以及 1.0 正式发布的验收标准还没定。**

## 二、新变化里最值得记的五件事

1. **收费做了一次完整的真实验，而且结论是拆墙。** 典藏付费曾以 ¥500 / 人民币 ¥25 一次性解锁真实上线（Stripe 真支付）；到 v0.60，现网支持页写得非常清楚：**游戏和导出都是免费的**，支持是纯自愿（定额 ¥300 / ¥500 / ¥1,000 / ¥10,000 或自选 ¥100–¥10,000），不换任何商品与功能，付错可全额退，特商法表记齐全。无论收入数字如何，这个顺序是对的：先证明有人愿意付，再发现免费 + 自愿更贴立意——但代价是收入强度与可预测性都降了一档，且见下条。
2. **国内玩家的支付通道是断的，支持页自己承认了。** “现在的支持通道只有银行卡，国内的卡多半刷不了。”对一个中文先行、首发中文圈的产品，这是变现的结构性短板，不是态度问题。如果作者判断现阶段受众以在日 / 海外为主，这个短板可以接受，但应作为明示取舍写进变现口径，而不是留在支持页的一句体贴话里。
3. **数据链这次真的闭环了——但读数仍未出现。** v0.56 有每日统计端点，v0.60.152 起 15 类事件全量镜像进 somme-commons（且镜像时剔除了能串起同一个人的访客编号，隐私口径与功能实现一致）。也就是说，“有没有人玩、玩没玩完、分不分享”第一次必然有答案了，只是答案从未以任何形式（哪怕 DEVLOG 里一行）公开或交付复评。收尾期验收如果没有这份读数，等于用手感验收一个数据齐备的产品。
4. **生产方式本身成了资产。** 286 个提交 / 9 天、CL 工单制、双树同种子逐屏比对、全池死种普查、年结刷屏这类真机问题（F1）靠玩家实拍定位——这套“AI 施工 + 人工裁定 + 校验门”的流水线在 DEVLOG 里留了完整账。它的价值超过任何单个功能：这是作者下一款产品可以直接复用的产能。
5. **收尾决议下对了。** v0.60.156 裁定：不再新开职业线、不再批量增厚，只剩修毛病、周末试玩复盘与最终验收。这个决议与本复评独立得出的判断一致——产品的边际收益已经在修呈现层的小毛病上（如工资年结的位置、手机页眉几像素的挤压），不在第 20 条职业线上。

## 三、新发现的问题（收尾期清单，按重要性）

1. **README 的“费用”一节已过期。** v0.60.162 的 README 仍写“一次性付 ¥500 解锁人生纪录典藏”，而现网支持页与实际功能都是“导出免费 + 自愿支持”。README 在 v0.60.122 的文档同步里被明确定为产品介绍的正本——正本写错收费状态，会误导玩家、合作方和任何按 README 评估的人。收尾期第一个提交就该修它（把 README 改到与 support.html 一致）。
2. **最终验收标准未定。** 版本号规则写明 1.0 = 正式公开发布，但什么数字算“可以发 1.0”没有任何一条：完局率、分享率、支持转化、真机试玩人数与问题清零标准都没有定版。建议把增长文档的健康线降格改写成验收线（完局 ≥55%、分享 ≥15% 之类不必全用，至少定完局率与“周末试玩 P0 问题清零”两条），写进 DEVLOG 后再谈 1.0。
3. **** 现网支持页页眉是“人生RESTART：如果那年”，游戏内与仓库名是《如果那年》。如果 RESTART 是有意的系列名，应在 README 与开始页统一出现；如果只是旧称残留，收尾清理时一并处理——品牌名在收尾期之后就不该再变了。
4. **** 挑战横幅与完局对照卡挂账三轮了。收尾决议下只有两个诚实选项：要么排进最终验收前的小清单（它们是裂变闭环最后两块），要么正式裁掉并在文档里销号——不要留着“计划中”的状态进入 1.0。
5. **** 内容许可写明文案与数据“保留所有权利”。共同开发继续下去之前，贡献的归属与署名口径（谁写的内容归谁、fork 里的提交如何算）最好由双方用一句话确认留痕——现在关系好，正是定这句话成本最低的时候。

## 四、评分项复评（简评）

- **立意 9.5。** 五条立场（出身靠发选择靠人 / 两条命一本账 / 事实先于文案 / 结局不分高下 / 对局零 AI）在 v0.60 全部从口号变成了可核查的产品事实：影子真模拟、结算只读账本、导出免费不卖改命。这是我给过这个项目的最高分，扣的 0.5 在品牌名未统一与 README 口径失真——立意产品输不起口径事故。
- **游戏性 8.5。** 职业线 19 条整线闭环 + 岔路去年龄化 + 影子同规模拟 + 父母照护真影响寿命，系统深度已经不输同品类任何产品。剩下的天花板是品类本身：一局仍是“读 + 选”的长时阅读，进程与呈现层毛病（年结刷屏式问题）在真机上还会冒头，收尾期的试玩复盘正是对症的。
- **裂变性：机制 8.5，实测仍不判定。** 导出免费把分享物料的门槛降到了零，反馈与统计让作者第一次能看见玩家。判不了的是数字：在读数出现之前，任何“裂变成立 / 不成立”的话都是猜。
- **未来价值 8.0。** 收尾定型的内容资产（6,400+ 条）+ 可复现引擎 + somme-commons 共用基建 + sommeatlas 域名下的生态位，让它从“一个小游戏”变成了“一个作者宇宙的第一块地”。单作者风险与 0.x 版本状态是主要折扣。
- **变现能力 4.0（维持）。** 实验精神与合规完成度（Stripe、退款、特商法）值得肯定；但自愿支持的收入天花板、国内支付断链、B 端与日文版仍不在图上，决定了它短期内是“能回一点血的免费产品”，不是“有收入模型的生意”。如果作者对它的定位就是前者，这个 4 分不是贬义，是口径对齐。

## 五、给收尾期的五条建议（不新增大功能）

1. 修 README 费用一节，与 support.html 对齐（今天就能做）。
2. 出一次读数，哪怕只有四个数（访客、开局、完局、分享）+ 支持笔数，记进 DEVLOG——这是最终验收的入场券。
3. 定 1.0 验收线并写进 DEVLOG：至少含完局率一条数字线 + 周末试玩 P0 问题清零一条质量线。
4. 挑战横幅 / 对照卡二选一：排进验收前，或正式销号。
5. fork 同步改为固定动作：本次已用同步 PR 合并（内容与 v0.60.162 一致）；后续小步同步优先用 GitHub 的 Sync fork 保持快进，少留合并提交，方便对账。
